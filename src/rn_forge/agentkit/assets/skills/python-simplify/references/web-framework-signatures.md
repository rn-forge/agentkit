# Complexity signatures in Django, FastAPI, and SQLAlchemy code

Load this **in addition to** `python-complexity-signatures.md` when §1 detects a
web framework. That file is the substance; this one covers what changes when the
code sits behind an HTTP boundary and an ORM.

Two things are different here, and both change what counts as a finding:

- **The framework already implements half of what the code reimplements.**
  Django's ORM *is* a data-mapper; DRF serializers *are* a validation layer;
  FastAPI's `Depends` *is* dependency injection. Model-written web code
  routinely layers a hand-rolled version on top. The C-signatures apply with
  more force here, not less.
- **Some output is a contract with clients you do not control.** A response
  body, a status code, a URL, a queryset's ordering. See *Behaviour classes*
  at the end — the base skill's three classes are not enough for a web app.

## W1. A repository layer over the ORM that adds no behaviour

`UserRepository.get_by_id()` whose body is `User.objects.get(pk=id)` or
`session.get(User, id)`. Often with a sibling `ListUsers`, `SaveUser`, and an
interface above it with one implementation.

**Fix.** Delete the layer; call the ORM from the service. **Trap.** The seam is
load-bearing when the tests actually substitute it, or when a second backing
store exists. Check the test suite before calling it speculative — this is C1's
trap, and it fires more often in web repos than anywhere else.

## W2. A service layer that is a pass-through

`UserService.get_user(id)` → `repo.get(id)` → `Model.objects.get(pk=id)`. Three
frames, no decision at any of them. The tell is a service class where every
method body is one line and the method names match the repository's exactly.

**Fix.** Keep the service only for methods that make a decision, span two
models, or own a transaction boundary. Route the rest at the view. **Trap.** Do
not collapse a service whose one-line methods are the *transaction* boundary —
`@transaction.atomic` on the service method is behaviour.

## W3. The same fields declared three times

An ORM model, a Pydantic schema, and a serializer, each restating the same
twelve fields — plus the `UserCreate` / `UserUpdate` / `UserInDB` / `UserOut`
ladder generated by reflex where two of the four have identical bodies.

**Fix.** Collapse the ladder to the shapes that genuinely differ at the boundary
— usually "what a client may send" and "what a client may see" — and derive the
rest (`model_config`/`Meta.fields`, inheritance, or `create_model`). **Trap.**
Do not unify the *input* and *output* schema to save a class. They diverge the
first time a field is write-only (a password) or read-only (an id), and
re-splitting them later is an API change. Two schemas that look identical today
but sit on opposite sides of the boundary are not duplication.

## W4. `async def` around blocking I/O

An `async` endpoint calling `requests.get`, a sync DB driver, `open()`, or
`time.sleep`. It blocks the event loop for every other request. The inverse tell
is just as common: `async def` with no `await` in the body at all.

**Fix.** Either make the call actually async (`httpx.AsyncClient`, `asyncpg`,
the async engine) or make the endpoint `def` — FastAPI runs a sync endpoint in a
threadpool, which is correct and is not a workaround. **Trap.** This one is a
`changes-output` finding under load and a `preserving` one in the test suite,
which will happily pass either way. Say so in the plan; do not let a green suite
argue it was cosmetic.

## W5. Cross-relation attribute access inside a loop

The web instance of `D1`. A queryset iterated with `item.author.name` per row,
or a template doing it. **Fix.** `select_related`/`prefetch_related`, or
`selectinload` — one query, and the fetch becomes visible at the point the data
is fetched instead of scattered across the loop.

**Trap.** Not every N+1 is a finding. On a bounded set — an admin page over ten
rows, a management command over a config table — the explicit loop is clearer
and the fix is noise. Report it only where N is user-controlled or unbounded.

## W6. Business logic in the view or the serializer

An endpoint body of sixty lines: validate, branch on role, mutate three models,
send an email, build the response. Or the same logic hidden in
`serializer.create()` / a Pydantic `@field_validator` that writes to the
database.

**Fix.** Move the decision into a plain function that takes and returns data —
testable without an HTTP client or a request factory. The view keeps parsing,
authz, and status-code selection. **Trap.** Do not build a service *class* to
hold one function; W2 is the failure at the other end of this fix.

## W7. Signals and event hooks where a call would do

A `post_save` receiver that every reader has to find by grep to answer "what
happens when I save this?" Model-written Django reaches for signals to avoid
editing a caller.

**Fix.** Call the thing explicitly from the one place that saves. **Trap.**
Signals earn their keep across an app boundary you do not own — a third-party
model, `django.contrib.auth`'s user. Keep those; name why in the plan.

## W8. Re-implemented framework behaviour

Hand-rolled pagination next to DRF's paginator, a bespoke permission check per
view where one policy class would serve, a custom exception handler that
reproduces `HTTPException`, manual `dict` building where the serializer already
renders, hand-parsed query strings next to a schema.

**Fix.** Delete and use the framework's. **Trap.** Verify the framework's
version actually matches the current behaviour — an off-by-one in a page
boundary or a changed error body is `changes-contract`, not `preserving`.

## W9. Settings and dependency sprawl

Four `Settings` classes, an env var threaded through six call sites with one
value, `Depends` chains resolving constants, or a `get_db` dependency wrapped in
three layers of factory. This is C4 and C6 in framework clothing.

**Fix.** One settings object, read once at the edge. Inject the settings object,
not the values. **Trap.** `Depends` for a *request-scoped* resource — a session,
the current user — is the framework working as designed. Only the
constant-valued chains are the finding.

## What is not a finding here

- **DRF/FastAPI declarative sparseness.** A five-line `ViewSet` that generates
  seven endpoints is idiom, not hidden complexity.
- **Django's fat model.** Logic on the model is the framework's stated
  convention. It becomes a finding at God-class scale (W6 / the "reason to
  change" test), not on principle.
- **Migrations.** Verbose, generated, and append-only by design. Not
  comprehension debt, and editing them is a correctness risk with no
  readability payoff.
- **A serializer that mirrors a model.** That is the boundary being explicit.
  Only the three-way restatement in W3 is the finding.
- **Framework boilerplate you did not write** — `settings.py` blocks, `asgi.py`,
  `apps.py`, generated clients.

## Behaviour classes for a web app

The base skill classes each finding `preserving`, `changes-output`, or
`adds-surface`. Add a fourth, and rank it above the others in §4's ordering:

**`changes-contract`** — the change is visible to a client you do not control: a
response field or its type, a status code, an error body, a URL or its
parameters, a default ordering, a header, a schema published at `/openapi.json`.

Two consequences for the plan:

1. A green test suite does **not** discharge a `changes-contract` finding. The
   suite is your assertion of the contract, not the client's. Name the
   consumers, or say plainly that they are unknown.
1. `changes-contract` phases go last, get their own commit, and carry the
   versioning or deprecation step *inside the phase* — not as a follow-up. A
   phase that ships a changed response body with no version note is the one
   phase in this plan that can break someone at 3am.

The ordering therefore reads: **preserving → changes-output → adds-surface →
changes-contract.**
